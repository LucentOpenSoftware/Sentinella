# Sentinella v0.1.13 — Web protection

The feature release: Sentinella can now block malicious domains at the DNS
layer, before a connection is ever made. A local DNS proxy (`dnsguard`)
answers on `127.0.0.1:53` and Windows is pointed at it through an NRPT rule —
built under one non-negotiable constraint: **under any uncertainty the system
degrades to "no filtering", never to "no DNS".** A machine that cannot
resolve names is broken in a way a machine without domain blocking is not.

The release also carries the largest defect-hunting pass this project has
run: 91 confirmed findings across the whole shipping surface, 85 of them
closed here. 62 predate this release — they shipped in 0.1.12 and earlier.

> **Web protection ships OFF by default in this release**, and there is
> deliberately no GUI switch for it yet. See *Known costs and limitations*
> before turning it on.

## Install / Upgrade

**Existing v0.1.12 installs** auto-update from the GUI (the update is signed
with the same key; the manifest signature was verified to name this exact
installer before publishing).

**Fresh install / manual upgrade**: download `Sentinella_0.1.13_x64-setup.exe`
below and run it elevated.

**First start takes longer than it used to** — see behaviour changes.

## What's new

### Web protection (preview, off by default)

- **A boot-time reconciler owns NRPT state, not the daemon.** `sentinelld`
  installs the DNS rule only after a four-step self-test proves its own proxy
  answers correctly, and refuses to install it at all unless the out-of-process
  reconciler task (`sentinella-dnsreconcile`, registered by the installer)
  exists — because that task is the only thing that can remove the rule when
  the daemon is not around to. A daemon that dies, hangs, or is killed
  mid-flight cannot leave the machine pointed at a dead resolver.
- **The rule GUID is recorded before the rule is written**, so a missing
  state file proves no rule was ever created rather than leaving an orphan
  nothing can name.
- **A watchdog re-proves liveness every 20 s** — with independent counters
  for "answers at all" and "actually resolves", and a busy-is-not-dead rescue
  so an overloaded proxy is not torn down by its own load shedding.
- **Upstream resolvers are discovered from the live adapters** and
  re-discovered every 30 s (VPN connect, Wi-Fi switch, DHCP renew) — never
  hardcoded to a public resolver, and a failed re-discovery keeps the last
  working list rather than an empty one.
- **The uninstaller removes the rule before deleting the binary that knows
  how**, and refuses to proceed if it cannot — an uninstall must never strand
  a catch-all DNS rule with nothing left to undo it.

### Calmer signature-update behaviour

A failed update fetch no longer interrupts you. The old behaviour raised a
"Signature update failed" toast on any freshclam timeout — an event that is
almost always transient, self-heals within the 4-hour update cycle, and gives
you nothing to act on. Now: transient failures are retried inside one
10-minute budget, background failures wait silently for the next cycle, and
you are notified only when signatures are genuinely old — **14 days by
default**, configurable under Settings → Updates. A manual update you started
still reports its failure immediately: you asked, you get the answer.
Everything is still recorded in the activity log.

### The GUI now knows "starting" from "broken"

On a fresh install the daemon spends minutes compiling its signature database
before the IPC pipe exists. The GUI used to spend those minutes showing
"Daemon disconnected" over a perfectly healthy service — on the first screen
a new user ever sees. It now asks the Service Control Manager, shows *Engine
starting — loading signature database* with a spinner, and reserves the error
for a service that is actually gone. (A slow first boot could previously even
trip the crash-loop detector into audit mode; it no longer can.)

### Daily signatures actually ship now

The release staging only ever looked for `daily.cvd`, but freshclam applies
incremental updates as `daily.cld` — so every previous installer silently
shipped **no daily database at all**. The one database that changes every day
now travels in the bundle, which is most of why the installer grew to 140 MB.

## The scrub

Before cutting this release the whole shipping surface went through a
20-lens adversarial review: 181 candidate findings, each attacked by an
independent verifier instructed to refute it. **91 confirmed** (22 critical,
14 high, 23 medium, 32 low — 62 of them predating this release), 90 refuted.
85 are fixed here, 2 were rejected on inspection, 4 are deferred with written
rationale. The 22 criticals deduplicate to six defects; five ended in the
same place — the machine loses working DNS — and all six are closed.

Highlights beyond web protection:

- **The FISH ransomware shield's active response was unreachable in every
  shipped build** — its config was pinned to defaults at construction and no
  save path ever refreshed it. Suspend/terminate now actually applies when
  you enable it.
- **A CDN cool-down no longer counts as a successful update.** freshclam
  exits 0 when the ClamAV CDN has rate-limited you, without downloading
  anything; the daemon stamped "just updated" and the staleness signal could
  never fire again for the life of the process.
- **A self-deadlock in the update path** (log call under a non-reentrant
  lock) that could hang the daemon's entire IPC surface whenever
  `freshclam.exe` was missing.
- **Killed update runs no longer leak their staging directories.** The
  development machine had accumulated 66 of them holding 2.15 GB.

Every finding — file, line, failure scenario, and the evidence it was
verified against — is in
[`docs/SCRUB_0113_FINDINGS.md`](../SCRUB_0113_FINDINGS.md).

## Known costs and limitations

We would rather state these than have you discover them.

- **The NRPT write path has not yet been exercised on a live machine.** Every
  layer that guards it — the self-test, the reconciler precondition, the
  watchdog, the boot task, the uninstall ordering — is unit-tested, and the
  design fails toward "no filtering". But no VM snapshot run has yet watched
  a real rule get installed, survive a crash, and be reconciled away. That
  validation is the next piece of work, and it is why web protection ships
  off by default with no GUI toggle: enabling it today means editing
  `config.toml` by hand, and means volunteering for that first exercise.
- **`update_mirror` is currently inert.** The setting validates, saves and
  renders, but freshclam still uses its own hardcoded mirror config. Wiring
  or removing it is open.
- **The dnsguard response cache has no eviction policy** — once full (8 MiB
  byte-capped) it stops caching new names until entries expire. Correct,
  bounded, but a design decision still owed.
- **Seven locales are missing ~220 newer UI strings** and fall back to
  English. Machine-translating security-critical settings labels would be
  worse; real translations wanted.
- **Carried over from v0.1.12, all still true:** rescans of cached corpora
  are I/O-heavy by design; the kernel ETW runtime layer is still unconfirmed
  on live hardware; EtherHiding HTTP detection stays dormant; heuristic
  detection efficacy remains unmeasured.

## Verification

- `cargo test --workspace` — **1235 tests, all green.** `tsc --noEmit` clean.
- Release sanity: **34/34** (previously 33/1 — the failing check was the
  missing daily database, which had been passing only because the check
  demanded the wrong file extension).
- The freshclam-notification change went through its own adversarial review
  (29 candidates → 14 confirmed → all closed) before the full scrub.
- The updater signature was decoded and checked to name
  `Sentinella_0.1.13_x64-setup.exe` specifically, and `latest.json` was
  generated from the artifacts on disk — not copied forward from the
  previous release, which the old hand-written process made dangerously easy.
